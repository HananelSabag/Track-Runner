# ארכיטקטורה

## מבט-על

```
┌──────────────── שעון (:wear) ────────────────┐        ┌────────────── טלפון (:mobile) ──────────────┐
│  UI (Wear Compose M3)                         │        │  UI (Compose M3)                            │
│     ▲ StateFlow                               │        │     ▲ StateFlow                             │
│  ViewModels                                   │        │  ViewModels                                 │
│     ▲                                         │        │     ▲                                       │
│  RecordingService (foreground) ── ההקלטה      │        │  (הטלפון לא מודד; Duo — שאלה פתוחה)         │
│     │                                         │        │                                             │
│  קובצי אימון (מקור האמת) ─► SyncEngine ───────┼─Data──►│  SyncReceiver ──► קובצי אימון (מקור האמת)   │
└───────────────────────────────────────────────┘ Client └─────────────────────────────────────────────┘
                         ▲                                              ▲
                         └──────────── מודולי core משותפים ─────────────┘
```

שני עקרונות מחזיקים את הכול:
- **קובץ האימון הגולמי הוא מקור האמת בכל מכשיר.** ה-UI קורא רק ממנו (וממצב המנוע החי), אף פעם לא ישירות מחיישן או מהרשת.
- **המנוע חי בשירות, לא במסך.** ההקלטה ממשיכה כשהמסך כבוי, כשהאפליקציה ברקע, וכשה-Activity נהרס.

## מודולים

```
Track-Runner/
├── wear/                 אפליקציית השעון
├── mobile/               אפליקציית הטלפון
└── core/
    ├── model/            ✅ טיפוסי דומיין (Kotlin טהור)
    ├── diagnostics/      ✅ קריאת יכולות חומרה (Android)
    ├── gnss/             ✅ קריאת ה-GPS של המכשיר עצמו: דגימות ולוויינים (Android). אותו קוד בשעון ובטלפון
    ├── tracking/         ✅ ניתוח אימון: אזורים, עבודה/מנוחה, ספרינטים, דופק, וניתוח חי (Kotlin טהור)
    └── data/             ✅ קובץ האימון, המאגר, הרכבת המסלול, סיכומים, ושמות הסנכרון (Kotlin טהור)
```

**כללי תלות:**
- `wear` ו-`mobile` לא תלויים זה בזה. כל מה שמשותף עובר דרך `core`.
- מודולי `core` לא תלויים באפליקציות, ולא ב-UI.
- **כל מה שאפשר — Kotlin טהור.** המסנן, הסטטיסטיקות והפרוטוקול לא מכירים את Android, ולכן נבדקים בבדיקות JVM מהירות בלי אמולטור. זה מה שמאפשר את בדיקות ההרצה-החוזרת של ריצות מוקלטות.
- **בתוך כל אפליקציה: חבילות לפי פיצ'ר** (`run/`, `history/`, `devicecheck/`, `theme/`), לא לפי שכבה. פיצול לפיצ'ר-מודולים רק אם יהיה בזה צורך אמיתי — בגודל הזה זה רק מאט את ה-build.

## ההקלטה בשעון

```
gnssFixes() ───┐                         ┌──► SessionWriter ──► <id>.fast.part ──(סיום)──► <id>.fast
heartRates() ──┼──► RecordingSession ────┤
satelliteViews()┘   (חי מחוץ לכל מסך)    └──► כל שנייה: TrackAssembler ──► LiveAnalyzer ──► LiveState ──► המסך
                          ▲
                   RecordingService (foreground: location|health) מחזיק את התהליך חי
```

- **`RecordingSession`** — אובייקט אחד שמחזיק אימון מהחיפוש אחרי GPS ועד הקובץ השמור. המסכים רק צופים ב-`StateFlow` שלו. אותו מבנה כמו `SprintSession`.
- **`RecordingService`** — שירות חזית מסוג `location|health`. עולה כשנפתח מסך ההקלטה (כדי שה-GPS יתחמם לפני "התחל") ועוצר את עצמו כשהאימון נשמר. יציאה מהמסך לא עוצרת הקלטה.
- **שני דברים איטיים יוצאים מה-thread הראשי:** הכתיבה לדיסק (thread אחד, כדי שהסדר יישמר) והניתוח החי (ברקע, פעם בשנייה).
- **הניתוח החי הוא הניתוח הסופי**, על מה שהוקלט עד כה. אין מצב שנצבר בצד, אז מה שרואים על היד לא יכול לסטות ממה שיהיה בהיסטוריה.
- **מה לא נבנה עדיין:** `SpeedSource` כממשק עם כמה מימושים, ומסנן Kalman. כרגע יש מקור אחד (ה-GNSS של השעון) ומסנן חציון ב-`TrackAssembler`. שניהם מחכים לנתונים אמיתיים.
- **`ALGORITHM_VERSION`** (`core:data`) — כל סיכום שמור מסומן בגרסה. שינוי באופן הקריאה מעלה אותה, והסיכומים נבנים מחדש מהקבצים הגולמיים.

### ניתוח אימון ✅

מה שיוצא מהמסנן הוא רצף `TrackPoint` (זמן, מהירות, מיקום, דופק). מעליו רץ ניתוח שכבר כתוב ונבדק:

```
List<TrackPoint> + ActivityProfile ──► SessionAnalyzer ──► SessionAnalysis
                                          ├ WorkRestSegmenter   עבודה / מנוחה מתנועה
                                          ├ SpeedZones          חמישה אזורים, סטנדרטיים או אישיים
                                          ├ EffortDetector      ספרינטים וריצות מהירות
                                          └ HeartRateZones      אזורי דופק, עומס, התאוששות
```

- **`ActivityProfile`** הוא כל ההבדל בין ריצה לכדורגל: ספי אזורים וכללי מנוחה. `ActivityProfile.RUN`, ‏`ActivityProfile.football(topSpeed)`.
- **פונקציות טהורות:** אותן נקודות → אותו ניתוח. אין מצב פנימי, אין שעון, אין Android.
- **אותו קוד לחי ולסופי:** בזמן האימון השעון מריץ את הניתוח על מה שהוקלט עד כה (שעה = 3,600 נקודות, זניח); בסיום הוא רץ שוב על הכול. לכן מנוחה יכולה להתחיל "בדיעבד" מרגע העצירה.
- **`intensityOf(...)`** מתרגם רגע בודד למה שמוצג על השעון: מנוחה / קל / בינוני / סף / עצימות גבוהה.

## מודל הנתונים (`core:data`)

**אימון אחד = קובץ אחד.** אין מסד נתונים. הקובץ הוא טקסט, שורה לכל דגימה, ונכתב בהוספה בלבד בזמן ההקלטה:

```
FAST 1                      ← גרסת הפורמט
id=<uuid>
kind=FOOTBALL               ← RUN / FOOTBALL / SPRINT_TEST
startedUtcMs=…              ← מתי, לתצוגה
startedElapsedMs=…          ← נקודת האפס של כל הזמנים בקובץ (שעון מונוטוני)
device=OPWWE231
appVersion=0.4.0
maxBpm=187                  ← הדופק המרבי שהשעון השתמש בו (אם ידוע)
#
G,<זמן>,<utc>,<יש מהירות>,<מהירות>,<אי-ודאות>,<lat>,<lon>,<דיוק מיקום>,<כיוון>
H,<זמן>,<דופק>
M,<זמן>,END                 ← סיום מכוון. בלי השורה הזאת: ההקלטה נקטעה
```

| קובץ במאגר | מה הוא |
|---|---|
| `<id>.fast.part` | אימון שמוקלט עכשיו |
| `<id>.fast` | אימון שהסתיים. **עובדה** — לא משתנה לעולם |
| `<id>.summary` | הסיכום שלו. **נגזר** — מטמון שאפשר למחוק; נבנה מחדש כשגרסת האלגוריתם או המהירות המרבית שלך משתנות |
| `<id>.synced` | הוכחה שהטלפון אישר שהאימון אצלו (רלוונטי בשעון) |

- **למה קובץ ולא Room:** הקלטה היא הוספה של שורה בשנייה, וקריאה היא תמיד "כל האימון". זה בדיוק מה שקובץ עושה טוב. קובץ בהוספה-בלבד שורד קריסה מעצמו (מה שנכתב — קיים), הסנכרון הוא העתקת הקובץ, והכול נבדק בבדיקות JVM רגילות בלי אמולטור. מסד נתונים יתווסף אם יידרשו שאילתות שקובץ לא נותן.
- **אותו קוד בשעון ובטלפון** (`SessionStore`), כך שאימון הוא אותו דבר בדיוק בשניהם.
- **קורא סלחני:** שורה לא מוכרת, מפתח לא מוכר או שורה אחרונה חתוכה — מדולגים. כך שעון חדש יכול לדבר עם טלפון ישן ולהפך.
- **`TrackAssembler`** הופך את הדגימות הגולמיות למסלול שהניתוח קורא: מסנן דגימה בודדת שקופצת (חציון של שלוש), משמיט מהירות שאדם לא רץ בה (מעל 45 קמ"ש), ומצמיד לכל נקודה את הדופק הקרוב.
- **`SessionInsights`** מריץ את הניתוח המתאים לסוג (אימון → `SessionAnalyzer`, מבחן ספרינט → `SprintTestAnalyzer`) ומפיק `SessionSummary` לרשימות ולשיאים.

## סנכרון

הפרוטוקול המלא ב-[03-watch-phone-sync.md](../research/03-watch-phone-sync.md). מבנה הקוד:

- **מה עובר:** קובץ האימון כמו שהוא, דחוס ב-gzip, כ-`Asset` של `DataItem`.
- **`SyncProtocol`** (`core:data`) — הנתיבים והמפתחות, משותפים לשתי האפליקציות: ‏`/fast/session/{uuid}`, ‏`/fast/ack/{uuid}`.
- **`SyncEngine`** (שעון) — כותב ל-`DataClient` כל אימון שעוד לא אושר; עם קבלת אישור מסמן `synced` ומוחק את ה-`DataItem` הכבד.
- **`SessionReceiverService`** (טלפון) — `WearableListenerService`: שומר את הקובץ (כתיבה לשם זמני ואז שינוי שם, כך שאין חצי-אימון), וכותב אישור. אימון שכבר קיים לא נשמר פעמיים.

גרסת הפורמט קיימת מהיום הראשון כי שעון וטלפון יתעדכנו בזמנים שונים, וצד חדש חייב לדעת לקרוא צד ישן.

## שכבת ה-UI

זרימה חד-כיוונית: המסך מקבל `StateFlow<UiState>` מה-ViewModel ושולח אליו אירועים. ה-ViewModel לא מחזיק לוגיקה עסקית — הוא ממפה מצב מהמנוע ומהמאגרים.

- **שעון:** `AppScaffold` אחד → `ScreenScaffold` לכל מסך → `TransformingLazyColumn` לרשימות. ניווט: `SwipeDismissableNavHost`. המסך החי הוא `VerticalPager` של שני עמודים: מבט, ומתחתיו סיכום-ביניים וסיום.
- **טלפון:** Compose Material 3, מחסנית מסכים פשוטה (חמישה מסכים — בלי ספריית ניווט), מסך מלא (edge-to-edge), כהה בלבד. הגרפים והמסלול מצוירים ב-`Canvas`, בלי ספריית גרפים.
- **מה שחי מחוץ למסכים:** בשעון `RecordingSession` / `SprintSession`; בטלפון `PhoneData` (האימונים) ו-`PhoneSync`. מסך שנפתח רק קורא מהם, כך שאימון שמגיע ברקע מופיע בהיסטוריה פתוחה מעצמו.
- **צבעי המותג** מוגדרים פעם אחת בכל אפליקציה (`theme/FastTheme.kt`) ותואמים ל-[brand.md](../brand/brand.md).

## שירותים והרשאות

| | שעון | טלפון |
|---|---|---|
| Foreground service | `location\|health` (הקלטה), `location` (מבחן ספרינט) | אין |
| הרשאות | מיקום מדויק, חיישני גוף (דופק), התראות | אין |
| רקע | Ongoing Activity; ‏`WearableListenerService` לאישורים מהטלפון | `WearableListenerService` לקבלת אימונים |

הרשאות מבוקשות ברגע שצריך אותן ועם הסבר, לא בהפעלה הראשונה. **הטלפון לא מבקש שום הרשאה**: הוא לא מודד, ואת האימונים הוא מקבל מ-Play services.

## החלטות עיצוב שכדאי לזכור

- **למה לא KMP?** אין iOS בתוכנית. Kotlin טהור ב-`core` נותן את רוב התועלת (בדיקות מהירות, הפרדה נקייה) בלי המורכבות.
- **למה לא ענן?** פרטיות ואפס תחזוקה. המחיר: אין גיבוי אוטומטי מעבר לגיבוי של Android — מכוסה ע"י ייצוא.
- **למה לא convention plugins עכשיו?** חמישה מודולים. כשנגיע לשישה-שבעה וה-`build.gradle.kts` יתחילו להשתכפל, נוסיף `build-logic`.
